# 数据抢救工具

**用途**：从 SQLite 数据库文件里雕刻出**被误删的行**。

这不是常规功能，而是一套应急工具。写它是因为本项目真实发生过一次事故 ——
一次"清理测试数据"的 `DELETE FROM task` 把用户的真实待办一起删掉了。
SQLite 删除行时**不会立刻覆写页面内容**，因此那些行还能从文件里捞回来。

## 使用前提

> **必须在数据库副本上操作。** 先停掉应用，把
> `%APPDATA%\com.tower.todox\` 下的 `todox.db`、`todox.db-wal`、
> `todox.db-shm` 三个文件一起复制出来备份，再开始。
> 应用运行时的写入会复用空闲页，把待恢复的数据覆盖掉。

## 工作流程

```bash
cd tools/recover

# 1. 雕刻 task 表（输出 carved.json）
node carve-tasks.mjs

# 2. 雕刻 reminder / task_completion 表（输出 carved-extra.json）
node carve-reminders.mjs

# 3. 写回数据库（单事务，失败整体回滚）
node restore.mjs
```

`restore.mjs` 里写死了它只还原 `carved.json` 里的任务与它们对应的提醒档位，
并且用 `INSERT OR IGNORE` —— 万一某行还在库里，**绝不覆盖**现有数据。

## 原理

SQLite 的 DELETE 只是把 cell 从页的指针数组里摘掉、把空间登记为空闲块，
**字节本身保留**到被复用为止。

麻烦在于：空闲块自己的 4 字节头会覆写到那个位置，**正好破坏记录头里
"头部长度"那个 varint**，于是 SQLite 官方的解析方式（依赖头部长度）失效。

因此这里的做法是不解析头部，而是：

1. 在整份文件里扫描**形如 UUID 的文本**（主键总在记录值区的第一个字段）
2. 枚举序列类型区的起点，要求"依次读 varint 恰好走完到值区起点"
   且**类型个数恰好等于表的列数**
3. 按这些类型解码出全部列，然后做**语义校验**：
   主键是 UUID、`time_kind` 是四个合法值之一、时间字段符合 RFC3339、
   `priority`/`is_completed`/`revision` 在合理范围、
   时间基准与类型相符（截止型必须有 `deadline_at`，其余必须有 `due_at`）

第 3 步是关键：它让"恰好解出正确记录"成为唯一可能，避免把随机字节
误报成数据。**没有语义校验的雕刻工具会给出大量假阳性。**

## 局限

- 只支持**行内存储**的记录。若某张表用了溢出页（单个字段超过页容量的约 1/4），
  大字段会存放在溢出页里，这里的扫描不会跟随过去。
  当前 schema 的字段都很短，不受影响。
- 页面一旦被复用（新写入的数据落到同一位置），原内容就真的没了。
  **越早停止应用、越早备份，成功率越高。**
- 表结构（列名与顺序）写死在脚本里。改过 schema 后需要同步更新。

## 教训

这类事故的根源不是"删错了"，而是**用一个无差别的 `DELETE FROM` 去清理
"我以为是我造的数据"**。正确做法是：

- 清理测试数据时**按精确条件删除**（按标题或 ID），绝不清空整表；
- 或者更彻底：**永远不要在用户的真实数据库上做测试**。
  测试应当用临时目录里的独立数据库。
