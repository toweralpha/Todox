## 严重 1：自然语言创建的全天任务永远不会有提醒

**位置**：`commands/mod.rs` 的 `attach_local_offset` + `scheduler/mod.rs`

**问题**：输入「明天 买牛奶」这类只有日期、没有时刻的表达，`due_at` 落库为
`NaiveDate::to_string()` 的产物 `"2026-09-30"`（**10 字节，无时间部分**）。
而 `attach_local_offset` 只认两种带时间的格式，因此该值被**原样透传**；
调度器用 `DateTime::parse_from_rfc3339` 解析它时因长度不足 19 字节而失败，
于是 `continue` 跳过该任务。

**实测证据**（`tests/audit_repro.rs`）：

```
due_at 实际值 = "2026-09-30"（长度 10）
推导结果 = []          ← 该任务永远不会提醒
```

**影响范围与严重性**：这是**最常见的输入形态之一**（"明天要做X"）。
更糟的是失败是完全静默的 —— 提醒档位确实写进了库，
`catch_up_missed` 走同一个 `upcoming_reminders`，所以连"你错过了"记录都不会有，
设置里的「全天提醒钟点」对这条路径完全无效。用户看到任务带着日期躺在列表里，
但永远不会响，且没有任何线索指向原因。

**这是我引入的回归**：在秒级迁移那一轮我加了空格分隔格式，
却没处理"纯日期"格式。原有的 e2e 断言 `due_at.starts_with("2026-10-01")`
恰好放过了格式问题 —— 一个"看起来在测时间"的断言，实际什么都没测住。

**修复**：`attach_local_offset` 增加纯日期格式（补成当天 00:00，
具体提醒钟点由调度器的 `all_day_base` 统一规整）。这样修而不是在调度器里
"多试一种解析"，是因为**保持单一的不变量**——"库里的时间字段永远是完整
RFC3339 时间戳"——比在每个消费点各自容错更可靠。

## 严重 2：用户输入可触发 chrono panic，release 下直接杀掉整个进程

**位置**：`nlp/mod.rs`（`parse_duration`、`parse_date`）、`commands/mod.rs`、`Cargo.toml`

**问题**：`n * per_unit * sign` 里的 `n` 来自用户输入且**完全无界**。
chrono 的 `NaiveDateTime + TimeDelta` 在越界时**会 panic**（不是返回 `None`）。

**实测复现**（`tests/audit_repro.rs`，两个真实 panic）：

```
src\nlp\mod.rs:582    ← today + Duration::days(n * sign)
src\commands\mod.rs:242 ← now + Duration::seconds(offset)
```

触发输入：`13800138000小时后 回电`、`99999999天后 取货`、`99999999999999天后 取货`。
阈值约为 8.2e12 秒（「天」≥8 位、「小时」≥10 位、「分钟」≥12 位、「秒」≥13 位）。

**为什么定为严重**：

1. `Cargo.toml` 里 `panic = "abort"`，release 下没有 unwind ——
   **整个进程消失**，托盘常驻与所有提醒一起没了；
2. 前端在用户**输入停顿约 180ms 后**就调用 `parse_input` 做实时预览，
   因此用户还没点保存、只是在打字或粘贴，进程就可能已经消失；
3. debug 构建下 `n * per_unit` 本身还会算术溢出 panic。

**这个缺陷的成因值得记录**：同一个仓库在别处都设了上限
（`scan_number` 的 100_000、`MAX_OFFSET_SECONDS`、`MAX_INTERVAL`），
**只有时长与相对日期这两条入口漏了**。说明"每个分支各自设限"这种做法
本身就会漏 —— 漏掉一处不会有任何提示。

**修复**：把上限收敛到 `domain::time::MAX_DURATION_SECONDS`（10 年）与
`clamp_duration_seconds()` 一处，然后在**解析源头**（`parse_duration`、
`parse_date`）和**日期加法点**（两处 `Duration::seconds`）都调用它。
两处是刻意的防御性重复：解析层收敛保证语义正确，加法点收敛保证
"任何其它来源的 offset"也不会越界。

## 严重 3：导入文件的列名 SQL 注入

**位置**：`repo/export_repo.rs` 的 `import()`

```rust
let columns: Vec<&String> = obj.keys().collect();   // ← 完全来自外部 JSON
let sql = format!("INSERT OR REPLACE INTO {table} ({}) VALUES ({})", ...);
```

列名在 SQL 里处于**标识符位置**，无法参数绑定，只能字符串拼接。
表名来自白名单常量（安全），但**列名完全来自被导入的 JSON 文件**，
文件只要带 `"app": "todox"`、`format_version <= 1` 就通过校验。

**可利用性**：安全子代理实测确认，`"id, title) VALUES (?1, ?1) --"` 这类键名
可以生成语法合法、尾部被注释掉的单条 INSERT。多语句被 rusqlite 的
`MultipleStatement` 检查挡住，因此攻击者能力上限约等于"合法导入本身"。
**但真正要修的理由是**：它让"备份文件格式"变成了一种 SQL 方言，
任何未来放宽（改成 `execute_batch`、或表名也动态化）会立刻升级为严重漏洞。

**修复**：`filter_known_columns()` 用 `PRAGMA table_info` 取实际列清单做
**白名单**过滤。选择"丢弃未知列并继续"而不是"整体报错"，是因为备份可能来自
更新版本 —— 能恢复大部分数据比什么都恢复不了好。但被丢弃的列名会写进
`ImportSummary.ignored_columns` 并展示给用户：**静默丢弃就是静默的数据丢失**。

修复后实测输出：

```
ignored_columns: {"task": ["x) VALUES (NULL); DELETE FROM task; --"]}
task: 0 行受影响
```

**一个重要的审计教训**：修复前的测试"通过"了，但通过的原因是
**SQLite 自己因为"没有该列"而报错** —— 不是代码在防护。
若我当时就此收手，就会误报"安全"。断言"失败"不等于断言"安全"，
必须确认失败发生在正确的层次。

## 中等 1：「合并」导入静默删除本地数据

**位置**：`export_repo.rs`；前端 `Settings.svelte`

**问题**：`INSERT OR REPLACE` 在主键冲突时会**真的 DELETE 旧行再插入新行**，
从而触发外键的 `ON DELETE CASCADE` —— 本地的完成记录、提醒档位、子任务、
标签关联被静默删除；对 `recurrence_rule` 更会把引用它的 `task.recurrence_id`
置为 NULL，留下 `time_kind='recurring'` 却无规则的坏状态
（之后 `complete()` 会报"重复任务缺少重复规则"，用户无法理解也无法自行修复）。

安全子代理用内存库实测确认了级联行为（`PRAGMA recursive_triggers = 0`）。

**同时是一个 UX 陷阱**：前端用 `confirm()`（只有两个选项），
于是**点「取消」= 走合并模式** —— 用户想中止这个危险操作，
反而走进了会改动数据的路径，而文案写的是「按 ID 合并，两条都保留」。

**修复**（两处）：

1. 改用 `INSERT ... ON CONFLICT(id) DO UPDATE SET ...`（upsert）。
   走 UPDATE 路径，不触发任何外键动作。`UPDATE` 子句里排除主键列。
2. 前端改为**两步询问**实现真正的三路选择（中止 / 清空并复原 / 仅合并），
   并在执行前再确认一次。

## 中等 2：调度器运行期没有补发路径

**位置**：`scheduler/mod.rs`

**问题**：`catch_up_missed` 只在启动时调用一次，而 `next_firing` 只接受
严格未来的触发点（`scheduled_at > now`）。这造成三类真实漏弹：

1. **select 竞态**：定时器到点与 `wake()` 同时就绪时，tokio 的 `select!`
   会**随机**选一支。若选中 wake 分支，本次触发被丢弃；下一轮 `now` 已晚于
   `scheduled_at` 被过滤 —— 既不弹通知也不记 missed，永久消失。
   （窗口 = "定时器已就绪但 select 尚未被 poll"，线程被抢占时可达毫秒级。）
2. **notifier 阻塞**：`notifier::show` 是同步阻塞调用（PowerShell 冷启动
   数百毫秒），期间到期的另一条提醒会在下一轮被当成"过去"丢弃。
3. **睡眠/休眠/改钟**：tokio sleep 基于单调时钟，醒来后 `fire` 用的还是
   睡眠前算出的旧触发点（时间标签已不对），睡眠期间到期的提醒全部被过滤掉。

**修复**：

- 把 `catch_up_missed` 移进循环开头，**每轮都补发**。该函数是幂等的
  （`record_missed` 按 `(task_id, scheduled_at)` 去重），重复调用不产生重复记录。
- 给 `select!` 加 **`biased;`**，让定时器分支优先于唤醒信号 ——
  从根上消除"恰好到点时来了 wake 就把触发丢掉"的竞态。

## 中等 3：`reset_defaults` 不是原子的

**位置**：`repo/reminder_repo.rs`

**问题**：早期实现是"先在自动提交的语句里软删旧档位，再在另一个事务里创建新档位"。
两步之间只要第二步失败（外部工具持有写锁导致 `SQLITE_BUSY`、磁盘满、连接异常），
结果就是**旧档位已删、新档位没写** —— 该任务从此没有任何提醒，
而唯一的痕迹只是一行 stderr。用户只是改了一次时间类型，却静默失去提醒能力。

**附带的不一致**：`create_task` 在 `create_defaults` 失败时返回 Err，
但任务行已经提交（`TaskRepo::create` 是独立事务）→ 前端显示"创建失败"、
用户重试 → 出现重复任务；而 `create_task_from_text` 对同一失败却返回 Ok。

**修复**：软删与重建放进**同一事务**。为遵守 `std::sync::Mutex` 不可重入
（在已持有锁的情况下再调 `create_defaults` 会直接死锁），
把插入逻辑抽成接收 `&Transaction` 的自由函数 `insert_tiers`，
让"首次创建"与"重置"两条路径共用同一份逻辑。

## 中等 4：含 XML 非法字符的标题 → 提醒永久静默丢失

**位置**：`notifier/mod.rs`

**问题**：`xml_escape` 原先只转义 5 个 XML 元字符，**不处理 XML 1.0 非法字符**。
标题里任何一个 U+0000–U+0008 / U+000B / U+000C / U+000E–U+001F / U+FFFE / U+FFFF
都会让 toast XML 非法 → `LoadXml` 抛异常 → 通知失败。

**后果链特别隐蔽**：调度器在调用通知**之前**就已经 `mark_fired` 写入
`last_fired_at`，因此这条提醒**不会被重试、也不会进入补发队列** ——
用户永远看不到它，且没有任何提示。

安全子代理用**真实 WinRT 实测**了字符集：

```
U+0009/U+000A/U+000D  → OK（XML 允许的空白）
U+0000/U+0001/U+0007/U+000B/U+000C/U+001B/U+001F/U+FFFE/U+FFFF → FAIL 0xC00CE508
```

可达性：**导入路径 100% 可达**（导入不校验标题）。

**修复**：`xml_escape` 增加 `is_xml_illegal()` 判断，非法字符**替换为空格**
而不是直接删除（删除可能把两个词粘在一起），保留 `\t \n \r`。

## 中等 5：`fs` 权限"过宽"——**这个判断是错的，已纠正**

**这一条记录的是我自己的一个错误判断，值得保留。**

我在上一轮看到 `fs:allow-read-text-file` / `fs:allow-write-text-file` 没有
scope，就判定为"权限过宽"并加上了路径范围限制。安全子代理读了**依赖源码**后
指出这个判断是错的：

- `tauri-plugin-fs 2.6.0/src/commands.rs`：scope **为空**时对任何路径返回
  `PathForbidden`；
- `tauri-plugin-dialog 2.8.0/src/commands.rs`：save/open 成功后只把
  **用户刚选中的那一个文件**通过 `allow_file` 加进 scope。

因此**空 scope 才是最窄的配置**，等价于"只能读写用户亲手选中的那一个文件"。
我加的路径范围反而会破坏合法用例（用户无法把备份存到 `C:\temp\` 这类位置），
却在安全性上没有任何改善。

**已还原**为无 scope 配置。

**教训**：判断"权限是否过宽"必须结合**依赖的实际行为**，
而不是只看配置文件里"有没有写限制"。我当时的推理（"没写 scope 就是任意路径"）
是对 Tauri 权限模型的一个错误假设，而验证它只需要读一眼依赖源码。

## 轻微 1：`opener:default` 是从未使用的权限

前端零处调用 `openUrl` / `openPath` / `revealItemInDir`（全 `src/` grep 确认），
Rust 侧只注册了插件。该权限集等于把"用默认程序打开任意 http/https/mailto/tel URL"
授予窗口 —— 一旦 WebView 被注入脚本，这就是现成的钓鱼跳板。

**修复**：删除该权限、移除插件注册与 `tauri-plugin-opener` 依赖。

## 轻微 3：通知子进程可能无限阻塞调度器

**位置**：`notifier/mod.rs`

`Command::output()` 会无限期等待子进程退出。若 PowerShell 因杀软拦截、
系统卡顿或自身挂起而永不返回，调用它的调度器线程就**永久停摆** ——
之后所有提醒都不再触发，而用户只看到"提醒忽然不响了"。

**修复**：

- 改用 `spawn()` + 带超时的轮询等待（10 秒），超时则 `kill()` + `wait()`
  （必须 wait 否则留僵尸进程）；
- 用**绝对路径**定位 PowerShell，避免相对名被 exe 目录/CWD 的同名文件劫持。

**已核实不是问题**：notifier 不会堆僵尸进程、不泄漏句柄 ——
`output()` 内部会边读管道边 `wait`，子进程被回收、stderr 读干
（stdout 是 `Stdio::null()`，不存在"管道写满把子进程卡住"的经典死锁）。

## 轻微 4：导入无大小上限，且静默跳过畸形行

**修复**（部分）：

- 前端读文件**之前**先 `stat` 查大小，超过 100MB 直接拒绝并说明原因。
  原先整个文件会经 `readTextFile` → `JSON.parse` → 整包 IPC（约 3–4 倍放大），
  误选 GB 级文件会让 WebView 直接崩掉，而崩溃信息对用户毫无意义。
- 被丢弃的未知列现在会在导入结果里汇报（见严重 3 的修复）。

**未修复**：畸形行（非对象、空对象）仍会被静默跳过而不计数。
需要给 `ImportSummary` 加 `skipped_rows` 字段，属小改动但未在本轮完成，
已在 README 记录。

## 轻微 5：`core:default` 权限过宽

`core:default` 包含整个核心 API 的允许集合（200+ 项），而应用实际只用到
窗口显示/隐藏/聚焦与事件。

**评估后决定不改**：逐项列出实际需要的核心权限容易在后续开发中漏配，
而漏配的表现是"某个 API 突然不可用"这类难以定位的运行时失败。
这些 API 的利用同样需要先攻破 WebView，收益不足以抵消这个风险。
已在 README 记录为已知取舍。

## 检查过但确认安全的部分

| 检查项 | 结论与理由 |
|---|---|
| **死锁** | **不存在**。`Db::lock()` 是唯一加锁入口，全部 31 处非测试加锁点逐个核对完毕，函数体内均无第二次加锁。`uncomplete` 的 `self.get(id)?` 在前（guard 已随 return 释放）；`create_defaults` 的 `load()` guard 随 return 释放；`reset_defaults` 原用显式作用域（刻意为之）；`upcoming_reminders` 两次取锁是**顺序**而非嵌套；`complete_recurring_tx` 只收 `&Transaction`。全仓库**没有** `if let Some(x) = self.db.lock()?....` 这类"临时 guard 生命周期延长到语句结束"的写法 |
| **忙循环** | **不存在**。`next_firing` 只返回严格未来，`delta > 0` 恒成立，`to_std()` 不会失败；无任何周期性轮询，空闲 CPU 实测 0ms/25s |
| **watch 丢失唤醒** | **不存在**。`wake()` 用 `send_modify` 原地递增；tokio 的 `Receiver::changed()` 是"先比 version 再决定等待"，因此"下一次 changed() 之前"发生的 wake 一定被观察到。（原先的漏弹是 `select!` 分支语义问题，不是通道丢信号 —— 已用 `biased` 修掉） |
| **命令注入（PowerShell）** | **当前不可利用**。安全子代理用 PowerShell 解析器对真实模板做 AST 解析，测试了 `& < " '`、反引号、`$(...)`、`]]>`、以及"换行 + `'@` + `Write-Output INJECTED`"，全部 `parse-errors=0`，命令列表只有模板自身的命令。**但注释里的理由原先是不完整的**：兜住 here-string 不被闭合的其实是 `'` 被转成了 `&apos;`（闭合序列需要字面 `'@`），而 XML 文本内容**不要求**转义 `'`。子代理做了反事实验证：去掉 `'` 的转义，同一标题立刻变成注入面。**这是隐性且脆弱的依赖**，已在代码里写明原因并加测试锁定 |
| **路径穿越** | **不存在**。导出/导入路径全部来自系统对话框返回值，Rust 侧 `export_data` / `import_data` **不接受任何路径参数** |
| **SQL 注入（其余各处）** | `task_repo.rs` 与 `schema.rs` 的 `format!` 只用字面量常量；`stats_repo.rs` 的 `format!("-{} days")` 是 `clamp(1,365)` 后的整数且作为**绑定参数值**传入；其余 repo 全部参数化 |
| **前端 XSS** | 全项目扫描确认**未使用 `{@html}`**，Svelte 默认转义所有插值。13 处 `onclick={fn}` 是 Svelte 5 的事件绑定语法，不是字符串注入 |
| **导入事务原子性** | 已构造"先清空、再必定失败"的攻击，验证用户数据完整回滚（5 条 → 仍 5 条）。rusqlite 的 `Transaction` 默认 `DropBehavior::Rollback`，因此提前 `return` 也不会写入部分数据 |
| **表名白名单** | 恶意表名（`"task; DROP TABLE setting; --"`）被直接忽略，`setting` 表完好 |
| **畸形导入行** | 已测空对象、非对象（字符串/数字/null）、超长列名（10 万字符）。均被跳过，不 panic、不写入脏数据 |
| **unwrap/expect** | 逐条核对：`from_hms_opt(0,0,0)` 常量必然 Some；`days_in_month` 的 expect 因 RFC3339 恰好 4 位年（≤9999）而不会失败；`nlp` 的字符切片做了边界推演（恒 ≤ len 且 ≥ 1）；其余全在 `#[cfg(test)]` 内 |
| **锁中毒** | release 下**不可达**（`panic = "abort"` 无 unwind，Mutex 不可能中毒） |
| **网络** | 应用**完全无网络访问**（无 HTTP 客户端依赖），因此不存在中间人等一类问题 |
| **通知的"稍后提醒"按钮** | **事实上失效** —— toast 的 `todox://snooze` 协议既没有 deep-link 插件也没有 `on_open_url` 处理，点击不会有任何反应。已记录为已知限制（见下） |

## 审计方法的自我批评

1. **第一个注入测试"通过"具有误导性**。它断言 `result.is_err()` 且通过了，
   我最初以为"代码有防护"。实际通过的原因是 SQLite 自己报错。
   **教训：断言"失败"不等于断言"安全"**，必须确认失败发生在正确的层次。

2. **我误判了 `fs` 权限**（见中等 5）。错误在于用一个未经核实的假设
   （"没写 scope = 任意路径"）代替了读依赖源码。修复一个不存在的问题，
   反而制造了一个真实的可用性缺陷。

3. **"每处各自设限"这种模式本身会漏**。严重 2 的成因就是三处里漏了一处。
   现在上限收敛到单一常量，并在源码注释里写明"不要另设上限"。

4. **"看起来在测时间"的断言什么都没测住**。原有的 e2e 只断言
   `due_at.starts_with("2026-10-01")`，恰好放过了格式问题 ——
   而格式问题正是严重 1 的根因。断言的**强度**比数量重要。

5. **子代理的价值在于读依赖源码与实机验证**。两处关键纠正
   （`fs` 权限模型、XML 非法字符集）都来自"实际跑一遍/读依赖"，
   而不是读我自己的代码。这是我自己审计时最容易偷懒的地方。

6. **并发部分的结论可靠性低于有测试支撑的条目**。
   `sleep_for` 不忙循环、watch 不丢信号等结论是子代理**代码推演**得出，
   我没有构造出对应的运行期复现。
