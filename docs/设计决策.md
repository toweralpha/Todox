# Todox 设计决策

这份文档解释 Todox **为什么这样实现**。它不是使用说明（见 [README](../README.md)），
而是给未来的自己或贡献者看的：每个非显然的选择背后是什么权衡。

---

## 为什么是 Tauri 而不是 Electron

需求里明确要求"长时间后台运行而不占用大量内存"。Electron 的方案是
**每个窗口都带一个完整的 Chromium + Node.js 运行时**，空窗口起步就是 100 MB 以上。

Tauri 用系统自带的 WebView2（Windows 上是 Edge 的 Chromium 内核），
带来两个决定性的好处：

1. **不打包浏览器内核** —— 可执行文件只有 7.0 MB，而 Electron 应用通常 80 MB 起
2. **托盘常驻进程只有 28–33 MB** —— 因为关闭窗口时可以把整个 WebView 销毁

代价是：内存省下来了，但**窗口可见时仍然是 354 MB**（WebView2 自身的子进程）。
这个代价无法消除，只能通过"关窗即销毁"让它不常驻。详细数据见 README 的
「资源占用」一节。

### 为什么窗口不可见时要销毁而不是隐藏

Windows 上 `hide()` 只是让窗口不可见，**WebView2 的渲染进程仍然活着** ——
实测仍占约 320 MB。而 `destroy()` 会真正释放 WebView 资源。

实测：

| 操作 | 内存变化 |
|---|---|
| 启动并显示窗口 | 354.1 MB |
| 关闭窗口（destroy） | 32.6 MB（**释放 321.5 MB**） |

代价是下次打开需要重新创建窗口并加载前端（约 200–400 ms）。
对一个"想起来才打开"的待办应用，这个取舍明显值得。

### 实现上踩到的坑：`prevent_close()` 拦不住退出

最初我在 `on_window_event` 里用 `api.prevent_close()` + `window.destroy()`
来实现"关窗保留在托盘"。**实测发现进程仍然退出了**：当所有窗口都被销毁后，
Tauri 会自动触发退出流程。

正确的做法是同时拦截应用级的退出请求：

```rust
.build(context)?.run(|app, event| {
    if let RunEvent::ExitRequested { api, .. } = event {
        // 只有用户明确选择"退出"时才放行
        if !quitting.load(Ordering::Relaxed) {
            api.prevent_exit();
        }
    }
})
```

`quitting` 是一个由托盘菜单「退出」项设置的标志。这个 bug 只在真实运行中
显现，单元测试完全测不出来 —— 教训是**生命周期类的行为必须实机验证**。

## 调度器是唯一真相源，不物化"下一次提醒时间"

数据库里**不存**"下一次该提醒的时刻"。每次需要时，调度器从任务的
时间基准 + 提醒档位**重新推导**。

### 为什么这样做

如果物化（把算好的时刻写进库），就必须在所有这些情况里维护它：

- 任务时间被编辑
- 提醒档位设置被改
- 重复规则推进到下一轮
- 时区或夏令时变化
- 用户手动改系统时间

漏掉任何一种，物化的值就会变成**陈旧的谎言** —— 而且不会报错，
只会让提醒在错误的时刻触发或干脆不触发。

重新推导的代价是每次唤醒多做一次查询（微秒级），而正确性是免费的。
**唯一被物化的是提醒档位本身**（`offset_seconds`），因为它们相对于时间基准，
不随时间推移而失效。

## 空闲时零轮询

调度器用 `tokio::time::sleep_until(下一个触发时刻)` + 一个 `tokio::watch`
唤醒通道：

```rust
tokio::select! {
    biased;   // 定时器优先，避免到点时被 wake 抢走
    _ = tokio::time::sleep(sleep_for) => { fire(...) }
    res = wake_rx.changed() => { /* 数据变了，重新推导 */ }
}
```

没有 `setInterval`，没有周期性 tick。实测托盘空闲 CPU 为 **0 ms / 25 s**。

### `biased` 是必需的，不是优化

`tokio::select!` 在多个分支同时就绪时**随机**选一支。若定时器到点的同时
恰好来了一个 `wake()`，随机会选中 wake 分支，本次触发就被丢弃；
下一轮 `now` 已晚于 `scheduled_at`，被"只取严格未来"的条件过滤掉 ——
**既不弹通知也不记 missed，永久消失**。

加 `biased` 让分支按书写顺序求值（定时器优先），从根上消除这个竞态。
另外循环每轮开头都会调用 `catch_up_missed`，作为第二道防线。

## 领域逻辑与 IO 分离

`domain/` 下的模块是**纯函数**，不做任何 IO：

- `domain/recurrence.rs` —— 从规则推算下一次出现时间
- `domain/reminder.rs` —— 从时间基准 + 档位算出触发时刻
- `nlp/mod.rs` —— 中文时间表达解析

它们接收 `NaiveDateTime` 之类的输入，返回值，**不碰数据库、不读系统时钟**。

这样做的收益在测试上非常直接：这些模块的测试可以精确构造"现在是 2026-09-29
14:00"这种边界场景，不需要 mock 时钟、不需要建临时数据库。目前 241 个测试里
大部分是这类纯函数测试，跑完只要 0.9 秒。

`repo/` 层负责所有数据库读写，`commands/` 层负责把两者串起来并暴露给前端。

## 软删除 + 同步字段从一开始就在表结构里

每张业务表都有：

```sql
id          TEXT PRIMARY KEY,   -- UUID v4
updated_at  TEXT NOT NULL,      -- RFC3339 带本地偏移
deleted_at  TEXT,               -- NULL = 未删除
revision    INTEGER NOT NULL    -- 每次写入 +1
```

### 为什么用 UUID 而不是自增整数

自增 ID 在多设备上必然碰撞。如果将来要接云同步，用自增 ID 意味着要重写
整个主键体系 —— 那是最难改的一类改动，因为它牵涉所有外键。

UUID v4 的代价是索引略大、可读性差，但换来的是"将来不用改表结构"。

### 为什么要 `deleted_at` 而不是直接 DELETE

同步的本质是"把本地变更传播出去"。如果删除是物理的，同步方无从知道
"这条记录是被删了"还是"还没同步过来"，只能靠全量比对。

软删除让"删除"也变成一次普通的、可传播的变更。

### 为什么要 `revision`

用于检测冲突：两端都改过同一条时，比较 `revision` 就能发现，
而不必比较所有字段。

### 为什么时间戳存带偏移的本地时间而不是 UTC

这是本项目里少数几个"反直觉"的选择。待办应用里**"今天"这个概念完全由
用户所在时区决定**。若存 UTC，那么"今天要做的事"在跨时区或夏令时切换时
会出现整天错位 —— 而这个错误极难复现，因为它在开发者的时区里完全正常。

存带偏移的本地时间（`2026-09-29T14:30:00+08:00`），"今天"就永远等于用户
看到的那一天。额外收益是直接读写数据库时时间可读，调试成本远低于一堆 epoch 整数。

代价是跨时区同步时需要归一化比较 —— 这一点由 chrono 的 `DateTime` 比较
自动处理，因此不构成实际问题。

## 未来接入云端同步的方案

表结构已经为此准备好了，需要新增的是：

1. **`revision` 的全局化**：目前是本行自增。多设备场景需要一个逻辑时钟
   （如 Lamport clock）或设备 ID + 本地计数来保证可比性。
2. **`changelog` 表的消费方**：每次写入都会追加一条变更记录，
   但目前没有任何东西读它。同步时它就是"待推送队列"。
3. **冲突解决策略**：字段级还是行级？本项目的数据模型（任务、提醒档位、
   完成记录）适合**行级 last-write-wins + 完成记录用集合合并**
   （完成记录是单调追加的，天然可合并）。
4. **传输层**：需要一个同步端点。目前代码里**完全没有网络依赖**，
   这是"离线可用 + 无隐私风险"的保证，不应为了同步破坏它 ——
   同步应该是可选的、显式开启的。

## 通知：为什么不直接用 WinRT

`tauri-plugin-notification` 在 Windows 上**不支持通知内的操作按钮**，
而需求明确要求"通知里能直接完成 / 稍后提醒"。只有直接调用 WinRT 的
`ToastNotification` 才能承载带按钮的 toast。

### 但未打包应用弹不出 toast

Windows 只会为 **AppUserModelID 已注册**的应用显示 toast。注册需要满足其一：

1. 存在一个带该 AUMID 的**开始菜单快捷方式**（安装包会创建）；
2. 存在一个已注册的 **COM 通知激活器**（需要额外编译并分发一个原生 DLL）；
3. 由另一个"AUMID 已注册"的宿主进程代为弹出。

最初的实现直接用 WinRT 配一个自造的 AUMID，即依赖方案 1 ——
在 `cargo tauri dev` 或直接运行 exe 时**不成立**。结果就是提醒到点了、
数据库也记录了 `last_fired_at`，但屏幕上什么都没有。用户看到的是"没有反馈"。

**现在采用方案 3**：通过 PowerShell 调用 WinRT 弹 toast。
Windows 10/11 自带的 PowerShell 本身就是已注册的宿主，
由它弹通知不需要注册任何东西、也不需要额外 DLL。

代价是每次提醒启动一次 PowerShell 进程（约 100 ms、几十 MB 瞬时内存，
随即退出）。对一个每天只有几次提醒的应用可以接受；若提醒频率大幅上升，
应改为方案 2 的原生 DLL。

### 通知如何"显示在最上层"

用 toast 的 **`scenario="reminder"`** 场景 —— 这是 Windows 专门为闹钟/提醒
提供的语义，与普通通知有两点关键差别：

- 普通 toast 几秒后自动消失，用户没看到就永远错过；
  **reminder 场景会让通知持续停留直到用户主动处理**
- 在专注助手（勿扰）开启时仍能显示

### 两处必须注意的转义

内容嵌进 PowerShell 的 here-string（`@'...'@`），那个形式下 PowerShell
不做任何展开，因此**不存在脚本注入面**，也不需要 PowerShell 转义。
真正需要处理的是：

1. **XML 元字符** —— 未转义的 `&` 或 `<` 会让 `LoadXml` 解析失败
2. **XML 1.0 非法字符** —— U+0000–U+0008、U+000B、U+000C、U+000E–U+001F、
   U+FFFE、U+FFFF 都是非法字符，同样让 `LoadXml` 抛异常

第 2 点尤其隐蔽：调度器在弹通知**之前**就已经写了 `last_fired_at`，
因此失败的通知**不会被重试、也不会进入补发队列** —— 用户永远看不到它，
且没有任何提示。

**还有一个隐性依赖必须记住**：兜住 here-string 不被提前闭合的，
其实是 `xml_escape` 把 `'` 转成了 `&apos;`（闭合序列需要字面 `'@`）。
XML 文本内容其实**不要求**转义单引号。也就是说，如果有人为了"精简"
去掉单引号转义，here-string 就会可被闭合，**立刻变成真实的脚本注入面**。
有测试锁定这一点。

## 秒级提醒与 schema v2

`reminder.offset_seconds` 的单位是**秒**（v1 曾是分钟）。

这个改动来自一个真实的用户反馈："我输入 10 秒后提醒我，结果没有反馈"。
根因有三层：

1. 解析器的时长单位表里**根本没有「秒」**，于是这句话被当成
   *没有时间的普通任务*存进收件箱 —— 它压根没有安排任何提醒；
2. 内部单位是分钟，10 秒会被截断成 **0**；
3. 通知因为 AUMID 未注册而根本弹不出来（见上一节）。

修复涉及一次**数据迁移**（v1 → v2）：列改名并把已有数值 ×60。
迁移用 SQLite 原生的 `ALTER TABLE`，而不是"建新表→拷数据→删旧表"，
因为后者会连带影响外键与索引。迁移与换算都有专门的测试 ——
**算错 60 倍会让所有提醒整体偏移，而且不会报任何错**。

### 顺带发现的一个截断缺陷

`"30秒钟后"` 曾被算成 **3 秒**：因为「钟」前面是「秒」不是数字，
数字扫描只抓到 `"3"`。这类错误不报错、只会让提醒在完全错误的时间触发。

修法是加一道校验：**数字与单位之间不能夹着另一个时间单位字**。

## 时长的上限为什么要收敛到一处

chrono 的 `NaiveDateTime + TimeDelta` 在越界时**会 panic**（不是返回 `None`），
而 release 配置是 `panic = "abort"` —— **整个进程消失**。

最初的代码在三处分别设了上限（提醒偏移、重复间隔、数字扫描），
但**时长入口漏了**。输入 `13800138000小时后 回电` 就能让进程消失，
而前端在用户**打字停顿 180ms 后**就会调用解析做预览 ——
用户还没点保存，只是在输入，进程就没了。

现在上限收敛到 `domain::time::MAX_DURATION_SECONDS` 与
`clamp_duration_seconds()` 一处，并在解析源头与日期加法点都调用它。

**教训**：让每个分支各自设限，就一定会漏 —— 而漏掉一处不会有任何提示。
收敛到单一常量并在注释里写明"不要另设上限"，比多加一次检查更有效。

## 导入的列名为什么要过白名单

列名在 SQL 里处于**标识符位置**，无法参数绑定，只能字符串拼接。
而导入文件里的键名完全来自外部 JSON，是攻击者可控的。

这条路径的风险等级是最高的：入口是"用户打开一个 .json 文件"这样一个
再普通不过的操作，而恢复模式还会先清空数据。

现在用 `PRAGMA table_info` 取实际列清单做**白名单**过滤，
未知列被丢弃并汇报给用户。

**一个值得记住的教训**：修复前的测试断言 `result.is_err()` 并通过了，
看起来"有防护"。实际上通过的原因是 **SQLite 自己因为"没有该列"而报错** ——
不是代码在防护。**断言"失败"不等于断言"安全"**，
必须确认失败发生在正确的层次。

### 为什么是"丢弃并继续"而不是"整体报错"

备份可能来自更新版本导出的文件（未来新增了字段）。
能恢复大部分数据，比什么都恢复不了要好。

但被丢弃的列名会写进导入结果并展示给用户 ——
**静默丢弃就是静默的数据丢失**。

## 为什么导入用 upsert 而不是 INSERT OR REPLACE

SQLite 的 `INSERT OR REPLACE` 在主键冲突时会**真的 DELETE 旧行再插入新行**，
从而触发外键的 `ON DELETE CASCADE` —— 本地的完成记录、提醒档位、子任务、
标签关联会被静默删除；对 `recurrence_rule` 更会把引用它的
`task.recurrence_id` 置为 NULL，留下 `time_kind='recurring'` 却无规则的坏状态。

改用 `INSERT ... ON CONFLICT(id) DO UPDATE SET ...`（upsert）走 UPDATE 路径，
不触发任何外键动作。这样"合并"才真正做到了"保留本地数据、同 ID 以备份为准"。

## 统计的"今天"为什么不能用 SQLite 的 `date()`

统计模块要回答"今天完成了几条"。看似可以直接交给 SQLite：

```sql
-- 错误写法
SELECT COUNT(*) FROM task_completion
 WHERE date(completed_at) >= date('now')
```

这段 SQL 里有两个错误，而且它们**互相掩盖**，因此很难被发现：

1. **`date()` 会把带偏移的时间戳规范化成 UTC。**
   我们存的是 `2026-10-01T00:30:00+08:00`（带本地偏移是刻意的设计决定），
   而 `date()` 把它当成 UTC 时刻 → 得到 `2026-09-30`。
2. **SQLite 的 `'now'` 也是 UTC，不是本地时间。**
   需要显式写 `'now', 'localtime'` 才是本地时间。

两者都偏移了同样的量，所以在"比较两个日期"时看似自洽 ——
直到你注意到补零循环用的是 `chrono::Local::now()`（本地日期），
两边一对比才发现错开了一天。

**症状**：UTC+8 的用户在凌晨 0–8 点完成的待办被算到前一天，
"今天完成数"显示 0，而昨天那一栏多一条。

**正确做法**：我们存储格式的前 10 个字符**就是本地日期**，
直接用 `substr(completed_at, 1, 10)` 取出来，起始日期从 Rust 侧按本地时间
算好后作为参数传入 —— 不做任何 UTC 往返。
本地日期不需要也不应该经过时区转换。

**这个 bug 是被一个"脆弱测试"意外暴露的**：原测试写完成记录用当前时间、
断言"最后一天是今天"，平时都通过，只在本地日期与 UTC 日期不同的那几个小时里
才失败。修复时补了两个**确定性**回归测试 —— 它们刻意各插入
「昨天 23:59:59」与「今天 00:00:01」两条边界记录：
只测一个边界时，在某些时区或一天中的某些时段测不出问题，
两条都测才能保证任何情况下都能区分出正确与错误的实现。
（两个测试都用"临时改回旧实现"验证过确实会失败，不是空测试。）

## `core:default` 不包含任何"改变窗口状态"的命令

这是本项目踩过的一个代价不小的坑，值得单独写清楚。

Tauri v2 的 `core:default` 看起来像"核心功能的默认权限"，很容易让人以为
它涵盖了窗口的基本操作。**实际上它只包含只读的查询命令** ——
`is_visible()`、`inner_size()`、`scale_factor()` 之类。
凡是会**改变**窗口状态的（`hide` / `show` / `close` / `set_focus` /
`start_dragging`）都不在其中，必须逐项显式授权。

### 症状为什么极具误导性

悬浮窗的关闭按钮、`Esc` 键、以及"失焦自动隐藏"都调用 `window.hide()`。
缺 `core:window:allow-hide` 时，Tauri 会拒绝调用并返回一个明确的错误：

```
window.hide not allowed.
Permissions associated with this command: core:window:allow-hide
```

**但原代码把这个错误静默吞掉了**：

```js
try {
  await getCurrentWindow().hide();
} catch {
  /* 隐藏失败无需打扰用户 */
}
```

于是用户看到的只是"点了关闭按钮没反应、按 Esc 也没反应"，
而真正的原因（一行清晰的权限错误）永远不会被看到。

**教训**：`catch {}` 只在"失败确实无关紧要"时才用。
这里失败意味着核心功能完全不可用，属于必须暴露的错误。
现在改为写 `console.error` 并明确指出缺少哪项权限。

### 无边框窗口的拖拽区同样需要权限

`data-tauri-drag-region` 不是纯 CSS 特性 —— Tauri 会注入一段脚本
（`src/window/scripts/drag.js`），在 mousedown 时调用
`plugin:window|start_dragging`。因此**它同样需要
`core:window:allow-start-dragging`**。缺了它，无边框窗口拖不动，
而且同样是静默失败。

（顺带修正一个常见误解：Tauri v2 的拖拽区**不是**靠 `app-region: drag`
实现的。`global.css` 里那条 `app-region: drag` 只是额外加的，
真正起作用的是注入脚本调用的那个命令。）

### 当前需要的窗口权限

| 窗口 | 权限 | 用途 |
|---|---|---|
| `float` | `core:window:allow-hide` | 关闭按钮、`Esc`、失焦自动隐藏 |
| `float` | `core:window:allow-start-dragging` | 拖动无边框窗口 |
| `main` | `core:window:allow-start-dragging` | 拖动侧边栏标题区 |

**改动 `capabilities/*.json` 时请保留这三项。**
改完务必实际点一下悬浮窗的关闭按钮 —— 这个错误不会在编译期或单元测试里暴露，
只能靠真实点击发现。

## 关于 `std::sync::Mutex` 的不可重入

`Db` 是 `Arc<Mutex<Connection>>`，而 `std::sync::Mutex` **不可重入** ——
在已持有锁的情况下再次 `lock()` 会直接死锁（不是报错，是永久挂起）。

因此有一条硬性约定：**repository 方法之间不互相调用**。
需要复用逻辑时，抽出接收 `&Transaction` 的自由函数，让调用方在已经持有
锁/事务的情况下复用它。`reminder_repo::insert_tiers` 就是这样来的。

审计时逐个核对了全部 31 处加锁点，确认没有"持锁时再取同一把锁"的路径，
也没有 `if let Some(x) = self.db.lock()?....` 这类"临时 guard 生命周期
被延长到语句结束"的写法。
